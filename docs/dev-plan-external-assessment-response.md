## 0. 结论先行

1. **评估的方向判断成立，但其 P0~P3 清单与仓库现状大幅重叠**：逐条映射后，
   评估清单里约三分之二的条目在本仓**已闭环**（它有门禁、有集成测试、有执行台账），
   评估者看不到这些是因为它只读了公开说明。**不按它的清单原样施工**——那会把
   已闭环项重做一遍，真缺口反而排在后面。
2. **真正的缺口收敛为 6 项**（§3）：生命周期竞态故障注入（V1）、移动桥接对抗性
   测试与审计留痕（V2）、错误码 Rust↔前端漂移静态比对（V3）、Safe Mode 可见性
   （V4，条件触发）、性能基线采集（V5）、补丁退役条件与回归矩阵（V6）。
3. **评估命名的最危险趋势是对的**："新增维护层复杂度超过它保护的 DSH 本体"——
   与本仓自身缺陷 D8（验证工具规模超过产品代码）同源。回应不是停止建设元层，
   而是 **V6 + 既有文档预算纪律**：每一层维护负担都要有退役条件和看守。
4. **评估漏看了整个元层设施**（门禁唯一产地表、`plan-facts`/`doc-facts` 守卫、
   合成版本号模型 ADR-061、双通道机制），因此它给"文档与实现不同步"的风险评级
   偏高——那类漂移在本仓有守卫且已因此红过多次。这不削弱评估价值：它准确地指出了
   **守卫还没覆盖的那几条边**（§1 映射表里标 🔴 的行）。
5. **评估本人反对的几件事，本文同样列为明确不做**（§4）：拆 crate、重写 Runtime、
   重建插件沙箱、OS 级签名、为统一而统一 IPC。理由引用既有 ADR，不重新论证。

### 1.3 评估的可信度与边界（为什么这样映射）

- **它做对的**：① 开篇即声明"不能仅凭架构描述认定已实现"——与 §7 宣称纪律同构；
  ② 反复区分"设计存在"与"已验证"；③ 明确反对重写 Runtime、反对为拆分而拆 crate、
  反对先优化后测量；④ 抓住的真问题是**维护层复杂度是否赚回了稳定性**。
- **它的结构性盲区**：只读公开说明 ⇒ 看不到门禁总表、计划台账、执行记录，
  于是把大量已闭环项排进 P0/P1。按它的原清单施工，边际收益最低。
- **它因此低估的**：本仓"扫出来再校验"的门禁必须断言扫出数 > 0（§7.3 E5-空纪律）、
  文档预算纪律（S2-2）——这些正是治它所说"文档与实现不同步"的机制。

> 每个批次的判据都按本仓纪律写：**可证伪**（把防护打回旧写法必须红）、

### V1 — 生命周期竞态故障注入补强（🔴 P0）

**目标**：把评估 §3.2/§9.2 列的竞态窗口从"设计上应有"变成"测试钉住"。
**不做的**：不改 Supervisor 公开 API、不加 crate、不动 INV-6。

**前置（V1-0，测试卫生）**：2026-10-27 实测——`npm run gate -- --tier=fast` 的 cargo 步里
`dsh-host` lib 约 26/169 个测试因 `%TEMP%` 写入 `PermissionDenied`（OS 错误 5）失败，
而**单独跑 cargo 反复全绿**；清空临时目录残留（实测清出 1000+ 个 `dsh-*` 目录）、
单线程执行均不能复现/修复。已排除：磁盘满（余量 70G）、测试线程并发、进程风暴、
特定门禁（任一门禁后均复现，单独均不复现）。判性为**本机 Windows 环境瞬态 × 测试卫生债务**
的叠加：唯一名用 `{pid}-{墙钟秒}`、清理用 `let _ =` 忽略失败、创建用硬 `unwrap`。
V1 开工前先修三项：唯一名改原子计数器（同进程内不可能撞）；临时目录创建对
Windows 瞬态错误重试一次；清理失败至少 `log` 留痕。**没有这一步，V1 的故障注入
判据会时不时红在环境上而不是红在缺陷上**——那正是本仓最反对的"红灯噪声"。

**验收**：六窗各一条测试（core 层 `crates/dsh-host/tests/`，本机 `cargo test -p dsh-host` 可跑）；
先写"窗口 × 断言"覆盖矩阵，矩阵本身可证伪（删一个场景的测试必须红）。
**已知限制如实登记**：GNU 工具链下 `dsh-desktop` 测试二进制无法加载
（`docs/incidents/local-toolchain-limits.md`）⇒ 壳层断言（V1-2/V1-3）由 CI（MSVC）执行，
本机只跑 core 层。**不因这个限制降低判据强度**——壳层断言的缺席曾让 E3 边界裸奔过。

### V2 — 移动桥接对抗性测试与安全审计留痕（🔴 P0）

**目标**：评估 §6.2 的八项从"设计已有"变成"测试钉住 + 结论留痕"。

| # | 评估项 | V2 判据 |
|---|--------|---------|
| 1 | 默认不监听 LAN | 未启动配对时无 LAN 端口（探针断言绑定面） |
| 2 | 未授权 RPC 被拒 | 无 cookie 时 `/api/rpc` 不得获得授权响应；桥如实上报未授权 |
| 3 | 配对令牌随机性/有效期/重放 | `random_token` 长度与字符集断言；TTL 过期拒绝；**重放拒绝（现有 401 测试保留并纳入本批清单）** |
| 4 | 跨源请求不能绕过授权 | 跨源预检与直接请求都不得获得授权响应（判据写在 HTTP 层，不依赖浏览器行为） |
| 5 | 停止后凭证失效 | stop/退出 ⇒ listener 关闭 + 内存态（cookie/pairing/session）清空；旧凭证不得复用 |

**留痕**：审计结论落 `docs/incidents/mobile-bridge-audit.md`（按 §4 主题档案惯例：

`SECURITY.md`「明示边界」同步一句指向该档。
**安全约束落实**（生成前约束）：本批任何新增出站请求代码只允许 http/https，
发请求前校验 host 并拒绝 localhost/环回/私有/保留地址；桥对自身后端的 loopback
访问按裁定 5 豁免，但在审计档里写明理由。

### V6 — 补丁行为回归与退役复核触发（P2）

> ⚠️ **更正（2026-10-27 复审）**：退役条件**并非缺失**——`patch-layers.mjs` 的 `retireWhen`
> 字段已逐补丁登记且 `auditPatchLayers` 强制非空，`LAYERS.md` 按包名列有"退役条件"列。
> 评估 §2.4 清单里真正还没守卫的是两件事：**①补丁改了运行时行为时没有对应的回归测试
> （改坏的补丁仍能过组装+分级门禁）；②上游发布新版本时没有触发退役复核的机制**——
> `retireWhen` 写的是"官方做 X 时退役"，而没人盯着上游做没做 X。

**动作**：
1. 给 `patch-layers.mjs` 的 `why` 字段补一个可证伪判据：每个 `functional` 层补丁
   （缺失即启动失败的少数）必须在 `crates/dsh-host` 或 `scripts/` 里有一条**移除补丁即红**
   的回归测试指向（写在 `why` 末尾，格式固定，由门禁解析）；
2. `verify-patch-layers.mjs` 的审计面加一条：解析每个补丁的 `retireWhen` 与回归测试指向
   是否可解（指向的路径必须存在；扫出数 = 补丁文件数，扫出 0 判红）；
3. `verify-upstream-drift.mjs`（sentinel 档）加信息层一行：上游发布新版本时打印
   「以下补丁的 `retireWhen` 可能需要复核」清单（只打印、不判红——退役与否是人工裁决）。

**判据**：把一个 `functional` 补丁的回归测试指向删掉/指成不存在路径必须红；
把 `retireWhen` 删空必须红（此条已有 `auditPatchLayers` 强制，本批只是把它的覆盖
从"非空"推进到"可解"）。**不与 `dev-plan-upstream-alignment.md` 的 G7/G11/G12 重复**——
那份提案守的是"上游变化要不要推版本"，本批守的是"上游变化要不要动补丁"，两个判据出口不同。
