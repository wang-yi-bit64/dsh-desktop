# ADR-051 — 已归档能力的已知缺口登记口径

| | |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-09-22 |
| 唯一产地 | 本节 + `AGENTS.md` §7.2 的归档行 + `docs/archive/plugin_isolation_architecture.md` 的已知缺口段 |

## 背景

ADR-040 / ADR-041 把「插件分级隔离」「多模型工具网关」裁定为**已归档**：代码删除、
文档移入 `docs/archive/`、README 与 §7 同步收敛。两份 ADR 的「后果」段都留了一句
前置条件式的表述——ADR-040 写「**同进程的插件崩溃仍可能带走 Harness**」。

问题出在这句话的**位置**：它写在 ADR 里，而 ADR 回答的是「为什么不是别的样」，
不是「现在缺什么」。于是产生一个真实发生过的事故（2026-09-22）：

用户按菜单进了安全模式、重启、问题依旧，读遍 README 与 §7.2 也找不到「哪些情况下
安全模式**不会**起作用」的说明。归档状态（🗄️）本身在说「插件隔离这条路我们不走了」，
但**没有回答**「那第三方插件坏了我能怎么办、哪里会失效」。缺口是沉默的：读者只会
在归档表里看到「已归档」，然后合理地以为「没写就是没问题」。

这不是文档不够多——`AGENTS.md` §7.3 已经规定归档要写明**判据**。缺的是另一件事：
**判据说明「为什么不做」，缺口说明「不做之后代价落在哪」。**

## 决策

1. **登记位置固定在 §7.2**：已归档能力若有用户可感知的残留影响，必须在
   `AGENTS.md` §7.2 的**该归档行内**（`↳` 子行，不得另起一行冒充新能力）显式登记，
   而不是只写在 ADR 的「后果」段里。理由是分工：§7.2 管能力状态，ADR 管决策理由
   （`docs/adr/README.md` 规则 5）——「现在缺什么」属于状态。

2. **状态词固定用 🗄️，不得用 ⚠️**：这是本条最容易被写错的一处。缺口挂在一个
   **已归档**的能力上，因此它只能由「恢复那个能力」来修——按 §7.3「归档是欠债已
   销账」，它不是欠债，也就**不该用 ⚠️ 未接线**。用 ⚠️ 会同时踩两个坑：
   （a）§7.3 明令「不要用『以后可能做』软化已经裁定不做的决定」，⚠️ 隐含「有批次
   在销账」；（b）`verify:claims` C3 会把 §7.2 里**任何** ⚠️ 行当作未登记欠债报错
   （`UNWIRED_ALLOW` 是空表且必须保持空——那是目标状态）。所以正文写「已归档能力
   的已知缺口」，状态词用 🗄️，缺口的四项内容写在证据列与调用方列里。

3. **字段固定为四项**，缺一不可：

   | 字段 | 回答的问题 | 反例（写了等于没写） |
   |------|-----------|---------------------|
   | 缺口 | 具体**不会**发生什么 | 「隔离不完整」 |
   | 判据 | 为什么不修 | 「复杂度高」 |
   | 恢复前提 | 什么条件下才重开 | 「以后再看」 |
   | 现场级证据 | 用户能看到的**具体现象**（日志行 / 界面表现） | 「可能有问题」 |

4. **表述口径**：只写**缺口本身与判据**，不得出现「已实现 / 已支持 / 基本可用」
   这类能力宣称；也不得为了让文档显得完整而把缺口改写成「计划中」——按 §7.3，
   归档不是计划中，不要用「以后可能做」软化已经裁定不做的决定（ADR-007）。

5. **缺口不得用代码补**：登记的是「已知且已裁定接受」的缺口，因此
   **禁止在任何单一权威之外另立特例分支**来绕开它——典型反例是在
   `projectGenerations()` 里加「安全模式就跳过第三方插件」的分支。那是
   在 `desired.json` 之外另立第二权威，正是 ADR-007 禁止的做法
   （同一事实两个产地，必然漂移）。要真解决，走恢复前提：与官方 loader 对齐。

## 备选方案与取舍

- **只写在 ADR 里**（原状）：否决。ADR 按编号聚簇、按「决策」检索，用户排查问题时
  不会去翻；而且它回答的是「为什么不做」，读者得自己推导出「所以现在会怎样」。
  2026-09-22 的事故就是这条路的实例。
- **新建 `known-gaps.md` 汇总页**：否决。多一个「事实二产地」——缺口修好后
  极容易只改一处（ADR-055 式漂移）。缺口天然属于「某个能力的现状」，就该长在
  §7.2 那一行上。
- **把缺口降级成「未实现」**：否决。「未实现」是**缺口 + 未裁定**（不得对外宣称，
  债还挂着）；这里是**已裁定接受**的缺口——性质不同，混用会让读者以为有人在修。
- **在 `projectGenerations()` 里打补丁绕过**：否决。见决策 5。

## 后果

- §7.2 表里出现第一种「不是欠债、不是计划、也不是纯结论」的行：归档能力
  **残留影响**。它挂在归档行下面（`↳`），因此不会污染「五状态词表」。
- 归档一个能力时多了一步必做动作：**写出它的缺口**。这会让「归档」的代价进入
  决策视野，而不是归档后装作无事发生。
- 代价：§7.2 表会长。接受——这张表的用途就是让陌生人能自查，长而准胜过短而漏。

## 守卫与证据

- `AGENTS.md` §7.3 新增「归档一个模块时」的第四条：登记残留缺口（字段见决策 3）。
- 首个按本口径登记的实例：插件隔离的残留缺口（进安全模式也**不会**隔离插件），
  登记在 §7.2 归档行的 `↳` 子行，判据与恢复前提引 ADR-040 与
  `docs/archive/plugin_isolation_architecture.md` 的「已知缺口」段。
- **无自动门禁**（诚实声明）：缺口是自然语言判断，脚本判不了。能守的只有格式——
  登记项必须四字段齐全，靠评审与 `grep -A3 "🗄️"` 人工核对。

## 附带发现：登记这个缺口的过程当场暴露了一处**空洞通过**

写本 ADR 的同时按 ADR-031（门禁必须可证伪）复核了相关守卫，抓到
`scripts/verify-harness-entry.mjs` 的 E5 在**扫零个模块**的情况下输出全绿：

`siblingModuleImports()` 只认 `from './x'` 与 `import('./x')` 两种写法，而入口
（`build/harness-node-entry.mjs`）在同期把兄弟模块加载改成了
`loadSiblingModule({ specifier: './x.mjs' })`——第三种形态，扫描器不认。于是
「三份打包清单漏登记兄弟模块」这条**唯一**的守卫静默失效，而那正是
v0.7.0-alpha.1 装出来的应用 `ERR_MODULE_NOT_FOUND` 的真实事故。

修法见该脚本：补第三条正则 + 新增 **E5-空** 断言（入口必然有兄弟模块，收齐 0 个
只能是扫描器失效）+ 6 项可证伪自检。**这是本仓第二次踩同类问题**（第一次是
`verify-claims` C3 的表格解析），因此这条经验值得独立成规矩，已加进
`AGENTS.md` §7.3 的「跨语言断言必须可证伪」条：

> **凡是「从源码里扫出 X，再校验每个 X」的守卫，必须同时断言扫出的数量不为 0。**
> 只断言「扫到的都合规」会容忍「一个都没扫到」——而那等于门禁替一段不存在的检查背书，
> 比漏报更危险。扫出数为 0 时，先怀疑扫描器，再怀疑源码。
