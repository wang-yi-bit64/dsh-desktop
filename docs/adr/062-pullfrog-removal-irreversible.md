## 背景

维护者 2026-10-09 指令：**移除 `.github/workflows/pullfrog.yml`，并在文档中写死「已移除且不可恢复、禁止重新启用」**。

**为什么 ADR-058 不够**：它已经把文件删掉了，但决策 1 把「恢复」写成了一个**正当选项**——「恢复 = 从 git 历史（commit `574f61e`）取回文件并重新过 ADR-054 的准入」。于是禁令的实际形态是**一段散文**。散文没有执行者。实测结果：

| 时间 | 事件 | 当时的门禁反应 |
|---|---|---|
| 2026-09-30 | `9f7ec0e` 按 ADR-058 删除文件 | — |
| 其后 | `d286f44`「Restore `pullfrog.yml` workflow」**恢复了该文件** | **没有任何检查报红** |
| 2026-10-08 | `47380f6` 重钉它的两个 action 到 40 位 SHA | 规则 B 只查「有没有钉 SHA」——文件回来后反而变成它的**服役证明** |

这不是一次疏忽，而是「禁令只写在散文里」这条形态的必然结果：**恢复文件不需要通过任何检查**；而文件一旦在，规则 B 会把它当正常在役的工作流去校验——**守卫在为它的复活背书**。

## 决策

1. **文件保持删除**。`.github/workflows/` 里不再有 `pullfrog.yml`（施行本 ADR 的提交包含这次删除）。
2. **禁令写死成机器判据**：`scripts/verify-github-config.mjs` 新增**规则 E** 与导出的 `RETIRED_WORKFLOWS` 禁令表，登记 `.github/workflows/pullfrog.yml` 及不可恢复日期；**文件重新出现 ⇒ `verify:github-config` 报红**。判据是**文件存在性**，不扫内容——本仓两次踩过「『不得出现』类判据被自己的文档命中」的坑，存在性判据没有这个失效模式。
3. **禁令表不得清空**（空集判据）：清空 `RETIRED_WORKFLOWS` 等于把禁令删掉，而那种删除同样静默 ⇒ **空表报红，不得冒充通过**（AGENTS.md §7.3 的「扫出 0 个不得判通过」）。
4. **正当出路是另立，不是复活**：将来确需按需 agent 时，**新建一份工作流**（新文件名 + 新 ADR 过 ADR-054 的准入）。若确要推翻本禁令，必须先显式改掉本 ADR 与禁令表——那是**有意的摩擦**，不是流程障碍。
5. **ADR-058 其余决策继续有效**：pr-agent.yml 零改动在役、无仓库内「停用开关」的中间态、secrets 处置分离（13 个 provider key 在仓内已无消费方）。本 ADR **只关闭决策 1 的恢复路径**，不推翻别的。

## 备选方案与取舍

- **只在文档里再写一遍「不可恢复」（不动守卫）**：否决。这正是 ADR-058 的原形态，已被 `d286f44` 证伪过一次；再写一遍同一形态的散文，等于把上一次实验重做一遍。
- **用 `git filter-repo` 之类抹掉历史里的该文件**：否决。历史不可逆改写会伤及 tag / Release 的可追溯性（本仓对「已发布 tag 不得改写」有明确纪律——ADR-058 那条删除动作的取证本身也依赖 `574f61e` 还在）。禁令靠判据实现，不靠抹掉来源。
- **用 `.gitignore` 或本地 git hook 挡**：否决。两者都不是仓库内容——新克隆、CI、其他维护者都看不见，与 ADR-058 已否决的「GitHub UI 停用开关」属**同一失效模式**（裁决写在一个进不了 git 的地方，ADR-007）。
- **把「退役禁入」通用化成可配置的路径黑名单**：本届不做。当前只有一个条目，通用化要先回答「哪些路径禁入」的元规则，属过度设计；现有表结构已足够承载后续条目（加条目时按表内注释要求同写 ADR 与消费方核查）。

## 后果

- 禁令从**散文**变成**可执行判据**：恢复文件会让 `verify:github-config` 变红，而不是静默通过。
- `verify:github-config` 自检项数 28 → **36**（新增 8 项 E 夹具，含两条可伪证断言：「文件重现必须报红」「禁令表被清空必须报红」）。同时**把自检项数改为计数器打印**——此前的「28 项」是手写值，已经随断言增删失真是本仓记录在案的同类缺陷。
- ADR-058 决策 1 的恢复路径关闭；ADR-058 的其余决策与原文保留供追溯。
- **代价（如实登记）**：将来若确需恢复，必须先改守卫与 ADR。这是**有意**的摩擦——因为上一次的「低摩擦恢复」已经真实发生过一次，且无人察觉。

## 守卫与证据

- `npm run verify:github-config` 实跑：规则 E 输出「退役工作流禁令：1 项在册 · 复活 0 项」，全量真检查 exit 0（扫描 9 个 YAML / 工作流形态 5 个 / uses 引用 31 个 / 错放 0 / 未加引号标量 100）。
- 可伪证夹具（`--self-test`，E 段 8 项）：喂 `.github/workflows/pullfrog.yml` **必须报红**；喂 `[]`（文件缺席）必须通过；喂其它在役工作流**不得误报**；**喂空禁令表必须报红**；反斜杠路径（Windows 分隔符）必须同样命中。夹具形态取自真实历史（`d286f44`），不是假想分支。
- 仓库侧证据：`.github/workflows/` 目录内容即判据——pullfrog.yml 缺席 ⇒ 该工作流不存在（GitHub 只从该目录加载；ADR-058 背景第 1、2 条）。
