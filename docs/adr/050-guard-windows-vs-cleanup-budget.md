# ADR-050 — 门禁的等待窗口必须与异步清理的预算对账

| | | |
|---|---|---|
| 状态 | 已接受 |
| 日期 | 2026-09-21 |
| 唯一产地 | `build/parent-death-watchdog.mjs`（两个常数 + 文件头「预算」表）、`scripts/verify-harness-entry.mjs`（E6） |

## 背景

孤儿清理是**异步**的：宿主死亡后，子进程不是立刻消失，而是由某个机制在之后把它收走。
各平台的机制与延迟不同，于是「多久之后才干净」是一个真实存在的常数：

| 平台 | 回收机制 | 延迟 |
|------|---------|------|
| Windows | Job Object（内核级） | 实测 ~216ms |
| Linux | `PR_SET_PDEATHSIG`（内核投递 SIGTERM） | 取决于进程对 SIGTERM 的响应 |
| macOS | **Node 侧看门狗**（轮询 → SIGTERM → 兜底强退） | 最坏 `POLL_INTERVAL_MS + FORCE_EXIT_MS` |

而门禁侧的断言是**同步**的：「杀掉宿主 → 等 N 毫秒 → 数一数还有没有孤儿」。N 与上面
那个延迟分处两个文件，各自看都合理——**对不上账时没有任何东西会报错**。

2026-09-21 的实况把这条链走完了：修好安装包缺文件（ADR-049）之后，macOS 的
`L2.2 关闭后无新增孤儿 node` 反而转红。两个原因叠加：

1. **那条断言在缺文件时是空洞通过的**——Harness 在 macOS 上根本没起来（正是 ADR-049
   的事故），没有进程可以成为孤儿，于是「无孤儿」永远成立。修好之后它才第一次
   真的测到了东西。**一条从未失败过的断言，可能从未运行过。**
2. 看门狗的最坏预算当时是 `250 + 1500 = 1750ms`，而 `smoke-launch.mjs` 的 L2.2 只等
   **1500ms** 采样一次；`fault-inject.mjs` 的 B 场景同样是 1500ms。真实 Harness 收到
   SIGTERM 后并不立刻退出（实测由兜底计时器决定退出时刻），于是采样点落在清理完成
   之前。**看门狗有单测、门禁有断言，两边都是绿的，只有真跑到 macOS 上才偶发一条红色
   ——而那条红看起来像是平台问题。**

## 决策

**两条，缺一不可：**

1. **断言「在预算内清理干净」，而不是「某个固定时刻恰好已经干净」。**
   `smoke-launch.mjs` 的 L2.2 改为轮询至 5000ms，并把**实际清理耗时**写进 detail
   （`清理耗时 ≈216ms`）。固定延迟 + 单次采样把「异步清理」测成了「定时竞态」：
   即使实现完全正确，也可能因为几十毫秒的抖动而随机失败，而随机失败的断言会被
   当成噪声忽略——那正是它开始失去意义的时刻。
2. **常数之间必须对账，且由门禁强制。** `verify:harness-entry` 新增 **E6**：从
   `build/parent-death-watchdog.mjs` 读出 `POLL_INTERVAL_MS` 与 `FORCE_EXIT_MS`，算出
   最坏预算，逐个比对 `fault-inject.mjs` 的两处孤儿检查窗口与 `smoke-launch.mjs` 的
   轮询上限；预算 ≥ 窗口即报错。

同时把看门狗的 `FORCE_EXIT_MS` 从 1500 调到 **750**（最坏预算 1750 → 1000ms），并在
该模块文件头立了一张「预算」表，写明两个窗口各是多少。宿主已经被杀了，没有任何人
在等这份收尾，750ms 足够让业务收尾代码跑完。

## 备选方案与取舍

- **只放宽门禁窗口（把 L2.2 等到 5s 就算完）**：否决。那样只是让断言更容易通过，
  而**清理实际有多慢**这件事仍然没人看着——用户关掉应用后残留 3 秒的 node 进程，
  门禁会一声不吭地放行。轮询 + 上报耗时同时解决「不误报」与「变慢看得见」。
- **只调小看门狗常数**：不充分。常数对了但断言仍是单次采样时，抖动照样能把它打红；
  而且下一次有人调常数时，没有任何东西会拦住他。E6 是让这类改动静默不了的那道闸。
- **把清理做成同步的（宿主退出前阻塞等待子进程）**：方向正确但不普适——
  macOS 上宿主是被 `SIGKILL` 的（`kill -9` 场景），它没有任何机会执行同步收尾；
  看门狗存在的理由正是「宿主没机会收尾」。所以异步预算是这个平台的固有属性，只能对账。
- **给 E6 加一条运行时验证（真跑一次杀宿主计时）**：那是 `fault-inject` 已经在做的
  事（A/B/E2 三个场景真杀真数）。E6 的价值在于**纯静态、秒级、在本地就能拦住**——
  把只在 macOS CI 上偶发的那类失败，提前到任何人改常数的当下。

## 后果

- 门禁的孤儿断言不再因清理抖动而随机失败；同时「清理变慢」以耗时数字的形式留痕。
- 改看门狗常数或改门禁等待窗口，都会被 E6 拦一次——改的人必须同时想清楚另一边。
- 代价：E6 依赖两处源码的字面写法（`const NAME = N`、`matchAll` 的 `setTimeout` 形态）。
  因此它在**解析不到任何东西时报错而非通过**，自检里也有「常数改名 → 必须报错」的
  夹具——守卫的失效必须比它守护的缺陷更早被看见。

## 守卫与证据

- `npm run verify:harness-entry` 的 **E6**，已进 `ci.yml` 与 release preflight。
- **可证伪性**（`--self-test`）：把看门狗打回修复前的 `250 + 1500 = 1750ms`，断言必须
  报超窗（这是真实的失败常数，不是构造出来的）；换成 `100 + 300 = 400ms` 必须通过
  （证明判定是「超窗才报」而非「见常数就报」）；常数改名必须报错而非静默通过。
- **本地实测**（2026-09-21，Windows）：
  - JobObject 路径：宿主被杀后入口进程 **216ms** 消失；
  - 强制看门狗路径（`DSH_PARENT_DEATH_WATCHDOG=1`）：**162ms** 消失，残留 0。
  - ⚠️ 这与「1000ms 预算」不矛盾：预算是**最坏**值（SIGTERM 被忽略时由兜底计时器决定），
    实测值取决于 Harness 对 SIGTERM 的响应速度。第一版测量脚本每次迭代都拉一个
    PowerShell（~0.3-0.8s），把结果量成了 1951ms——**测量工具的开销大于被测对象时，
    量到的是工具**。改为 `process.kill(pid, 0)` 内进程探测后数字才对得上。
- 相关：ADR-011（看门狗本身的三个坑）、ADR-049（让 macOS 的 L2.2 第一次真的运行起来
  的那次修复）。
