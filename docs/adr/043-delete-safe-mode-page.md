# ADR-043 — 删除 safe-mode.html

| | |
|---|---|
| 状态 | 已归档（2026-09-10 批次 C，随代码一并删除） |
| 日期 | 2026-09-10 |
| 唯一产地 | （已删除）`frontend/safe-mode.html`、`window::show_safe_mode_page` |

## 背景

安全模式引导页曾是一个独立页面。但批次 C 同时裁定：**不实现插件卸载/禁用**
（ADR-042）——而 `safe-mode.html` 的每处交互都要求「插件移除」后端。接上它，
交出的会是一个「其余按钮仍读空气」的页面：点了有反应的是进/退安全模式，
没反应的是卸载。

## 决策

整页删除，连同资源、配置项与 `window::show_safe_mode_page` 一并移除。
它的独有能力（进安全模式）已由三处覆盖：错误页「安全模式」按钮、
恢复页 `safe-mode` 动作、原生菜单 `harness-safe-mode`。

## 备选方案与取舍

- **保留页面但只留进/退安全模式两个可用按钮**：否决。半页可用半页读空气的页面
  比没有页面更糟——用户无法区分「坏了吗」与「还没做」。要么全接，要么删。
- **留页面等后端**：否决。同上，且违反「不为可能有用的未来预留」
  （ADR-005）。

## 后果

- 壳内静态页从 7 个收敛到 6 个，全部可达、全部有真实交互。
- 安全模式能力的入口收敛到错误页 / 恢复页 / 原生菜单三处，消除了「同一能力
  四个入口、其中一个是死的」这类宣称落差。
- ⚠️ 附带教训：「界面反馈（横幅）」仍是 🕓 计划中——上游靠 preload 注入
  (`mountSafeModeBanner`)，本仓界面**看不出**当前处于安全模式。这是明确的
  后置决策（等软件功能稳定），不是欠债。

## 守卫与证据

- `verify:ipc-surface`（删除的页面与命令不在登记表中；`local_page` 目标清单同步）。
- `AGENTS.md` §7.2 的 `safe-mode.html` 行（🗄️ 已删除，含删除文件名——否则下一个
  人只会看到「某个能力不见了」）。
