# Feature Log

> **这是什么**：`docs/version-policy.md` §3.1「唯一权威链路」的**第 2 步**产物（Feature Log）。
> 它把「上个 tag..HEAD」的提交**分类累积**下来，供第 3 步（Release Plan）判断「这一版该不该切、切什么类型」。
>
> **它的权威边界**：本文件**不是**版本号的产地，也**不**批准发布。版本号由 `release-manifest.json`
> （第 3 步）批准、第 4 步从台账派生。本文件只回答「上次发布之后，仓库里多了哪些改动」。
>
> **本轮标记**：曲线修复轮（`0.2.0-rc.2.2` / `0.2.1-alpha.1.2`）。上一轮（首轮合成号 `0.2.0-rc.2.1` /
> `0.2.1-alpha.1.1`）的同类清单已随 git 历史留档，本文件按「本轮」重写（§0.1 的基线因此前移）。

## 0. 本轮基线与生成方式（先读这段）

### 0.1 基线的选择：**两条线各有各的基线**

`§5.1` 步骤 2 写的是「上个 tag..HEAD」。**在两条通道并存时，「上个 tag」不是唯一的**——
首轮合成号两条线**同日各自发过**（2026-10-09），因此本轮的基线是**各通道自己的**上一个 tag：

| 线 | 上一条已发布 tag | 日期 | 区间内提交数 |
|---|---|---|---|
| `alpha`（目标 `alpha`） | `v0.2.1-alpha.1.1` | 2026-10-09 | **9** |
| `next` / rc（目标 `next`） | `v0.2.0-rc.2.1` | 2026-10-09 | **7** |

两条基线的差是 **2 条**（`8fa84f2` / `8d7aeb8`，即 rc 首轮发布那两个提交）——它们落在
alpha 基线之后、rc 基线之内。这是**两条线各自记自己的账**的正常结果，不是遗漏：
rc 线那次发布的东西已经通过 `v0.2.0-rc.2.1` 交付给 rc 用户了。

> ⚠️ **与上一轮相比，两条基线的间隔从 30 条缩到 2 条**：上一轮 rc 线一次性补齐了 30 条存量
> （见 git 历史里上一版本文件的 §3.3）。**本轮没有存量**——两条线只差那 2 条 rc 侧发布提交。
>
> 📌 **快照边界（结构性限制，不是笔误，也**不要**为了刷新数字而再加提交）**：
> 本表的计数是「**承载本文件的那次提交的父提交** `ba879bc` 之前」的全部提交。
> 本文件自己的提交、以及它之后的任何提交**按定义不在区间内**——写它的时候它们还不存在。
> 所以你在 HEAD 上原样复算会得到 **10 / 8**（各多 1 条 `docs`），差值就是本文件的提交本身。
> 上一轮同一格也是这个形态（其创建提交 `7946100` 未被计入）。`docs` 按 §2 第 11 行**不产生 `n`**，
> 因此这不影响版本判定。
>
> 🔴 **本轮有 2 条「发布准备途中」才落下的提交**（`7b2b087` / `ba879bc`，§3.1 第 5、6 条）：
> 它们都是在**跑这一轮流程本身**时撞到的发布机制缺陷。之所以能把它们并进本轮，
> 是因为它们落在**生成变更日志之前**（`§5.2①` 要求的「非发布提交先落」）。
> 这 2 条的成因同源：**本机 `core.autocrlf=true` 与「脚本只按 LF 写」的错配**。

### 0.2 上游锚点：**两条线在区间内都没有前进**

这是「为什么本轮不是 `upstream` / `mixed` 类型」的判据，逐条核对过：

| 目标 | 上一 tag 时的 `dshVersion` | HEAD 上的 | 结论 |
|---|---|---|---|
| `next` | `0.2.0-rc.2` | `0.2.0-rc.2` | 未前进 |
| `alpha` | `0.2.1-alpha.1` | `0.2.1-alpha.1` | 未前进 |

判据命令（唯一产地 `scripts/dsh-targets.mjs`）：

```bash
node scripts/dsh-targets.mjs --version-of next    # 0.2.0-rc.2
node scripts/dsh-targets.mjs --version-of alpha   # 0.2.1-alpha.1
```

⇒ 两个区间内**均无**上游前进 ⇒ 按 `§3.2` 排除 `upstream` 与 `mixed`；本仓**无** `feat:`
（见 §1）⇒ **`desktop-fix`**（`x.y.z` 不变、`n+1`）。

### 0.3 生成方式（如实声明，不冒充机器产物）

`§3.1` 的表格把 Feature Log 的所有者写成「**机器 + 人工复核**」，落点写的是 `feature-log.mjs`。

**该脚本目前仍然不存在**（全仓按 `**/feature-log*.mjs` 检索无命中）。因此本文件当前是
**人工按同一判据复核**写出的：分类规则与 `scripts/conventional-commits.mjs` 一致——
`parseCommit()` 解析、`classify()` 分组、`suggestBump()` 判版本位
（破坏性 → `major`；任一 `feat` → `minor`；任一 `fix` / `perf` → `patch`；
只有 `docs` / `chore` / `ci` 等 → `none`，即**不发版**）。本文件使用的「计入版本判定」一词
即指后者的前四类。⇒ 「机器生成」这件事**尚未落地**，不要把它读成已完成。

⚠️ 本轮的分类统计与破坏性判定**不止是人工看**：§1 与 §2 每一行的数字都由下面这组命令现算，
可逐条复现（`$BASE` 取该通道的上一 tag）：

```bash
BASE=v0.2.0-rc.2.1          # rc 线；alpha 线取 v0.2.1-alpha.1.1
git log --format='%s' "$BASE..HEAD" | grep -cE '^feat(\([^)]*\))?:'
git log --format='%s' "$BASE..HEAD" | grep -cE '^fix(\([^)]*\))?:'
git log --format='%s' "$BASE..HEAD" | grep -cE '^perf(\([^)]*\))?:'
git log --format='%s%n%b' "$BASE..HEAD" | grep -cE '[a-z]+(\([^)]*\))?!:|BREAKING CHANGE'
```
