# Feature Log

> **这是什么**：`docs/version-policy.md` §3.1「唯一权威链路」的**第 2 步**产物（Feature Log）。
> 它把「上个 tag..HEAD」的提交**分类累积**下来，供第 3 步（Release Plan）判断「这一版该不该切、切什么类型」。
>
> **它的权威边界**：本文件**不是**版本号的产地，也**不**批准发布。版本号由 `release-manifest.json`
> （第 3 步）批准、第 4 步从台账派生。本文件只回答「上次发布之后，仓库里多了哪些改动」。
>
> **本轮标记**：双线重锚轮（`0.2.2-rc.1.1` / `0.2.2-alpha.3.1`）。上一轮（双线重锚轮
> `0.2.1-alpha.5.1` / `0.2.1-rc.2.1`，更早是 alpha 单线曲线修复轮 `0.2.1-alpha.2.1`）的同类清单
> 已随 git 历史留档，本文件按「本轮」重写（§0.1 的基线因此前移）。

## 0. 本轮基线与生成方式（先读这段）

### 0.1 基线的选择：**两条线各有各的基线**

`§5.1` 步骤 2 写的是「上个 tag..HEAD」。**两条通道并存时「上个 tag」不是唯一的**——
两条线各自发过不同的合成号，因此本轮基线**按通道各取一条**（`changelog.mjs --print-baseline`
是同一套判据的机器实现，见 §0.3 的复现命令）：

| 线 | 上一条已发布 tag | 指向提交 | 日期 | 区间内提交数 |
|---|---|---|---|---|
| `alpha`（目标 `alpha`） | `v0.2.1-alpha.5.1` | `bfda0c2` | 2026-10-19 | **29** |
| `next` / rc（目标 `next`） | `v0.2.1-rc.4.1` | `25592b6` | 2026-10-29 | **4** |

两条基线的间隔是 **25 条**。这批提交**已经交付给 rc 通道**（`v0.2.1-rc.2.1` / `v0.2.1-rc.4.1`
两次发布把它们发出去了），但**从未交付给 alpha 通道**——alpha 上一次发版是 2026-10-19。
所以它们对 alpha 用户仍然是新的，**不能**因为「rc 侧发过了」就从 alpha 账上划掉。
两条线各自记自己的账，这是**正常结果**，不是重复计数。

> ⚠️ **`next` 区间本轮只有 4 条提交，但这一版仍然必须发**：判据不是提交条数，而是
> **上游锚点前移**（§0.2）——`0.2.1-rc.4` → `0.2.2-rc.1` 属 §3.2 的 `upstream` 面，
> `x.y.z` 必须前进。同时本仓在区间内另有需发版改动（2 条 `fix` + CD 批次 14 项缺陷修复）。
> **这类「提交数很少、锚点说必须发」的情形以锚点为准**——否则用户会永远停在旧运行时上，
> 而台账里那条在役键的 `builds[]` 永远是空的。

> 📌 **快照边界（结构性限制，不是笔误，也**不要**为了刷新数字而再加提交）**：
> 本表的计数是「截至**承载本文件的那次提交（`build(next)`）的父提交** `16ed343`（含）」的全部提交
> ——`16ed343` 自己（CD 批次交付）在两条线的表里都计入；复现本表数字时，把 §0.3 命令里的
> `HEAD` 换成 `16ed343`。本文件自己的提交、以及它之后的任何提交**按定义不在区间内**——写它的时候它们还不存在。
> 在本轮双 build 提交的 HEAD（`a68d598`）上原样复算会得到 **6 / 31**（rc / alpha 各多 2 条，
> 均为 `build`：`build(next)` 与 `build(alpha)`——本文件随 `build(next)` 承载，没有独立的
> `docs` 提交；若在其后的修订提交上复算，还会再多出该修订自身，同理不在区间内）。
> `build` 与 `docs` 一样不产生 `n`（`§3.1` 未计入），因此这不影响版本判定。

> 📌 **本轮是「单 PR 双提交」**：`build(next)` 先行、`build(alpha)` 随后。本文件与
> `release-manifest.json` 在两行上都已写**本轮批准的最终值**，因此若你在两个提交之间
> 跑 `node scripts/dsh-targets.mjs --version-of alpha`，会看到仍是旧值 `0.2.1-alpha.5`
> ——那是**尚未落地的同批改动**，不是本文件的错误。锚点翻转本身在 `build(alpha)` 提交里。

### 0.2 上游锚点：**两条线在区间内都前进了**（本轮的主因）

| 目标 | 上一 tag 时的 `dshVersion` | 本轮锚定 | 结论 |
|---|---|---|---|
| `next` | `0.2.1-rc.4` | `0.2.2-rc.1` | **前进**（minor 前进，且**跳过上游 `0.2.1-rc.5`**） |
| `alpha` | `0.2.1-alpha.5` | `0.2.2-alpha.3` | **前进**（minor 前进，同 minor 内跨 2 个预发布位） |

判据命令（唯一产地 `scripts/dsh-targets.mjs`）：

```bash
node scripts/dsh-targets.mjs --version-of next    # 0.2.2-rc.1
node scripts/dsh-targets.mjs --version-of alpha   # 0.2.2-alpha.3
```

⇒ 两条线**都有**上游前进，且**都**带本仓需发版改动（两线全部补丁改名重锚 + 三路合并迁移；
组装侧 PWA 图标适配）⇒ 按 `§3.2` 是 **`mixed`**
（`x.y.z` 前进、`n = 1`），不是 `upstream`（本仓并非零改动）、也不是 `desktop-fix` / `desktop-feature`
（`x.y.z` 已随锚点前进，`n` 按新组从 1 起算，与「`x.y.z` 不变、`n+1`」无关）。

### 0.3 生成方式（如实声明，不冒充机器产物）

`§3.1` 的表格把 Feature Log 的所有者写成「**机器 + 人工复核**」，落点写的是 `feature-log.mjs`。

**该脚本目前仍然不存在**（`ls scripts/feature-log*.mjs` 无命中）。因此本文件当前是
**人工按同一判据复核**写出的：分类规则与 `scripts/conventional-commits.mjs` 一致——
`parseCommit()` 解析、`classify()` 分组、`suggestBump()` 判版本位。
⇒ 「机器生成」这件事**尚未落地**，不要把它读成已完成。

⚠️ 本轮的分类统计与破坏性判定**不止是人工看**：§1 与 §2 每一行的数字都由下面这组命令现算，
可逐条复现（`$BASE` 取该通道的上一 tag）：

```bash
BASE=$(node scripts/changelog.mjs --print-baseline --version 0.2.2-rc.1.1)   # → v0.2.1-rc.4.1
git log --format='%s' "$BASE..HEAD" | sed -E 's/^([a-zA-Z]+)(\([^)]*\))?!?:.*/\1/' | sort | uniq -c
git log --format='%s%n%b' "$BASE..HEAD" | grep -cE '[a-z]+(\([^)]*\))?!:|BREAKING CHANGE'
```

`--print-baseline` 本身就是**按通道**取基线的实现，两条线的基线与上表逐字一致（alpha →
`v0.2.1-alpha.5.1`，rc → `v0.2.1-rc.4.1`）。

## 5. 与 Release Plan 的关系

第 3 步据此出计划（`release-manifest.json`）：

| 线 | `releaseType` | `n` | `w` | 派生出的合成号 | 上一版 |
|---|---|---|---|---|---|
| `alpha` | `mixed` | 1 | `null` | `0.2.2-alpha.3.1` | `0.2.1-alpha.5.1` |
| `next` | `mixed` | 1 | `null` | `0.2.2-rc.1.1` | `0.2.1-rc.4.1` |

`n = 1` 的含义：该 (上游精确版本, 通道) 组的**第 1 次**交付——两条**新**在役键
（`0.2.2-rc.1` / `0.2.2-alpha.3`）在台账里的 `builds[]` **均为空**。两条线的 `n` 各自独立递增，
**不共享序号**。旧键 `0.2.1-rc.4`（1 条构建）/ `0.2.1-alpha.5`（1 条构建）随锚点翻为 `dormant`，
其 `builds[]` **原样保留**——它们是已交付的历史，不参与新一轮的 `n` 计算。

> ⚠️ **`w` 取 `null` 是偏离 §3.2 的显式裁定**：该表对 `mixed` 建议「`w` 标批次」。本轮不取，理由：
> `+w` 会进安装包文件名与 `latest.json` 的 URL（多一处必须正确处理的 `+` 编码面），
> 而批次身份已由台账的 upstream 键 + `n` 唯一确定，且 `w` **不承担排序**（§1.3）。

|---|---|---|---|---|
