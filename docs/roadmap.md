## 2. 战略判断：两条外部曲线

项目的一切长期决策都由两条曲线决定。它们相互独立，但指向同一个结论。

**曲线 A — 上游是快速迭代的预发布版。** 官方 DSH 明确标注 developer preview，并声明会有破坏性
变更。本仓的补丁基线（`DSH_VERSION = '0.1.2-alpha.4'`，`scripts/prepare-harness.mjs:74`）已落后于
npm 上的 `0.1.5-rc.*` 若干版。**只要项目还靠 `patch-package` 改上游文件，这条曲线就会持续收税**：
`上游变更数 × 补丁数 × 运行时变体数`（见 `harness-packaging-and-compatibility.md`）。

**曲线 B — 官方桌面版已经进入上游仓库，且采用更深的宿主协议。** 上游 `apps/desktop` 是完整实现
（Electron、私有 `@deepseek-ai/dsh-desktop-host`、`dsh-app://`、不监听端口、版本与 dsh 锁死、
独占 `profiles/desktop`），只是尚未公开发布。它覆盖的正是社区壳的核心场景。

> **两条曲线的交点结论**：**"再做一个更漂亮的 DSH Desktop"这条路会持续贬值。**
> 产品价值必须搬到官方**不做**、或**做了也需要第三方补齐**的那一层去。

**这与仓库自己的判断一致。** `dsh-desktop-redesign-architecture-and-plan.md` §1.1 早已写明：
改造目标不是加功能，而是**重新划定职责边界**，警惕"桌面壳向第二套 DSH Runtime 演化"。
本路线图不是引入新方向，而是**把那份设计真正执行下去，并吸收批次 F 之后的现实**。

## 3. 定位声明

**从「另一个 DSH 桌面客户端」收敛为「DSH 的可靠运行时、兼容性与发行增强层」。**

一句话产品价值，五个词：**可靠、可诊断、可恢复、可兼容、可发行。**

### 是 / 不是

| 是 | 不是 |
|----|------|
| 面向复杂 DSH 环境的**运行时治理层** | 与官方桌面 UI 正面竞争的**聊天客户端** |
| 无 GUI、可复用的 **Runtime Supervisor**（`dsh-host`） | 第二套 **Agent Runtime / Agent Loop** |
| 兼容性、诊断、恢复、打包的**工程能力提供方** | 皮肤 / 桌面宠物 / 重做官方 Web UI |
| 官方 DSH 之上的一层**增益** | 官方 DSH 的**替代品** |

> 定位转变有一个**立刻可验证的连锁收益**（见 §7）：一旦"桌面产品"身份淡出，为它而存在的
> 3 个 `functional` 补丁（插件挂载相关）就失去了存在理由——**定位收缩直接换来补丁收缩**。

## 4. 边界原则（把"谁负责什么"写死）

采用既有五层模型（`dsh-desktop-redesign-architecture-and-plan.md` §3.1），**单向依赖**：

```
L1  Desktop Shell   —  Tauri / 窗口 / 菜单 / 托盘 / 更新 / 原生对话框 / 通知 / 桌面设置
        ↓
L2  Supervisor      —  dsh-host：spawn / ready / health / restart / orphan / logs / diagnostics / safe mode
        ↓
L3  DSH Runtime     —  官方 Node + DSH：Agent / Session / Tool / MCP / Cordis / Web UI
        ↓
L4  Extension       —  插件策略：官方同进程；社区插件可诊断可恢复；高风险按官方 loader 边界隔离
        ↓
L5  Compatibility   —  Provider / Tool-Calling 兼容层（**仅在满足复活判据时存在**，见 §8）
```

**禁止（违反即视为架构回归）**：
- DSH Runtime → Tauri UI 实现
- Plugin → 任意 Tauri IPC（本仓已是单向注入，见 INV-2）
- Provider 兼容逻辑 → 进 Tauri 窗口层
- Tauri Shell → Cordis 内部 registry

**本路线图的第一个交付物是一份边界契约文档**（见 H0 的 B1）：把"哪些问题由 DSH 负责、
哪些由 Desktop 负责"逐条列出。这是外部评审的建议第 10 条，也是后续所有裁剪的判据。
判据形式沿用本仓惯例——**每条都要能回答"它能不能在没有窗口系统的机器上被测试"（INV-6）**。

## 5. 兼容性治理：把"兼容"变成产品能力

这是本路线图相对既有文档**真正新增**的机制，也是曲线 A 的系统性解法。

### 5.1 兼容矩阵（Compatibility Matrix）

每个 release 记录并验证一组已证组合，而不是"能起来就算"：

| Desktop | Node | DSH | Plugin API | Web UI | 结果 |
|---------|------|-----|-----------|--------|------|
| 0.x | 24 | 0.1.2-rc.x | vX | vY | ✅ 已验证 |
| 0.x | 24 | 0.1.5-rc.x | vX+1 | vY+1 | ⚠️ 待验证 / 部分 |
| 0.y | 24 | 0.1.5-beta | vZ | vY+2 | ✅ 已验证 |

矩阵的**唯一产地**放在 `dsh-contracts`（与错误码总表同处），并由一个 gate 校验
"仓库里引用的 DSH 版本 ∈ 矩阵"。

### 5.2 运行时回归语料（Runtime Regression Corpus）

每个候选 release 自动跑同一条端到端脚本，作为"兼容性"的证据而非承诺：

```
clean startup → workspace open → session create → tool call → tool failure
→ plugin crash → recovery → update → restart → 三平台 smoke
```

> ⚠️ **诚实约束**：现阶段该语料主要验证**运行时行为**（能否起、能否恢复），
> 不承诺**模型语义正确**（Tool Calling 的正确性依赖 L5，见 §8 决策点 2）。
> 不要把"跑通了语料"表述为"模型调用正确"。

### 5.3 patch 退役机制（把 `retireWhen` 变成常规工序）

`patches/LAYERS.md` 已为**每一个**补丁写了 `retireWhen`（上游补齐什么能力后即可退役），
但它是"写下来"而非"被执行"。本路线图把它变成每个上游升级周期的**强制一步**：

1. 升级前逐个补丁对照 `retireWhen`，能退役的**先退役再加新补丁**（净减少 → 维护税下降）；
2. 目标：3 个 `functional` 补丁（插件挂载相关）随"桌面产品"身份收缩而被官方扩展点取代；
3. 每个 release 汇报"补丁数趋势"，进 CI job summary（与 `report-bundle-size.mjs` 同形）。

## 6. 阶段路线图

四个阶段 + 一条贯穿全程的轨道。时间以"投入"而非"日历"计，**每阶段独立可交付、可回滚**。

### H0 — 加固与边界固化（近端，2~4 周）· 🟡 进行中（H/J/K 已完成，I 部分）

> 2026-09-12 进度：批次 **H（风险哨兵）/ J（门禁可信度）/ K（宣称纪律）已完成**；
> **I（上游推进）部分完成**（预检工具与实测已交付，版本号推进待三平台验证窗口）；
> H0-f 边界契约、L（构建卫生）、M（运维韧性）尚未开工。详见
> [`dev-plan-hardening-and-differentiation.md`](dev-plan-hardening-and-differentiation.md) §6。

| 项 | 内容 | 依据 |
|----|------|------|
| H0-a | **风险哨兵**：上游漂移哨兵 + profile 保留名守卫 + 官方桌面约束文档 | 加固计划批次 H |
| H0-b | **宣称纪律回归**：修 README 过度宣称、`verify:claims`、§7.3 自查自动化 | 批次 K |
| H0-c | **门禁可信度**：GUI 冒烟与 POSIX fault-inject 转硬门禁；preflight 加秒级运行时防线 | 批次 J |
| H0-d | **构建卫生**：区域镜像去隐式、Node 口径统一、一行 bootstrap、清理重复资产 | 批次 L |
| H0-e | **运维韧性**：签名密钥 runbook、更新源故障演练、bus-factor runbook | 批次 M |
| **H0-f** | **边界契约文档**（§4）：逐条写死"归 DSH vs 归 Desktop" | 外部评审建议 10 |

**退出判据**：`verify:drift` / `verify:claims` 可用且带回退检查；三平台门禁全硬；边界契约文档入库。

### H1 — 资产化 `dsh-host`（第 2 个月）

把最有长期价值的资产（Supervisor / 诊断 / 恢复）从"桌面附属"变成**独立、无 GUI、可复用**的组件。

| 项 | 内容 |
|----|------|
| H1-a | `dsh-host` 保证**零 Tauri 依赖**（INV-6 已是此形状，此步是把它变成对外承诺并加 gate） |
| H1-b | CLI 面补齐：`start / status / stop / tail / doctor`（已存在）→ 增 `recover`；文档化为对外接口 |
| H1-c | 发布 `dsh-host` 为可复用 crate（本地 registry 或 crates.io 私发），供 CLI / 第三方壳 / IDE host / CI 调用 |
| H1-d | 用它自证：**用 `dsh-host-cli` 在无 GUI 环境跑通启动→就绪→恢复**，作为"层可独立"的证据 |

**退出判据**：`dsh-host` 可脱离 Tauri 编译与运行；一条 CLI 命令能完成"启动→崩溃→自动恢复"。
**战略意义**：此步完成前，"可靠层"只是口号；完成后，它**不依赖官方桌面的存亡**。

### H2 — 兼容性工程（第 3~4 个月）

| 项 | 内容 |
|----|------|
| H2-a | 落地 §5.1 兼容矩阵 + `dsh-contracts` 校验 gate |
| H2-b | 落地 §5.2 运行时回归语料（三平台），产出"兼容性证据" |
| H2-c | 执行 §5.3 patch 退役：随上游升级筛掉可退役补丁，汇报"补丁数趋势" |
| H2-d | 推进上游基线（加固计划批次 I），把补丁迁到当前 rc 线 |

**退出判据**：每个 release 都带一份更新的兼容矩阵 + 语料结果；补丁数不增或下降。

### H3 — 发行工程与定位固化（第 5~6 个月+）

| 项 | 内容 |
|----|------|
| H3-a | 可回滚的运行时更新事务（失败更新可恢复，不软锁用户） |
| H3-b | 发行质量：签名、SHA-256、runtime manifest、离线 runtime、国内 registry fallback、代理感知引导 |
| H3-c | 真实三平台端到端发布实验室（把冒烟从"手动档"升级为可调度回归） |
| H3-d | 定位固化：README / 品牌收敛为 "Runtime Reliability Edition"；明确与官方桌面的**互补**关系 |

**退出判据**：一次失败的更新能被自动回滚；三平台发布实验室可一键复现；对外表述与 §3 定位一致。

### 贯穿轨道 — 定位与边界（P，全程）

| 项 | 内容 | 时点 |
|----|------|------|
| P1 | **Linux 作为发行战术**（不是独立战略）：官方桌面明确不支持 Linux，本仓已有 deb/AppImage 与 linuxdeploy 经验——把 Linux 出包提升为一等公民（CI 必过、README 首屏标注） | 随 H0~H3 并行 |
| P2 | 与官方桌面的关系维护：跟随上游 `apps/desktop` 演进，评估"补充而非竞争"的具体形态（见 §8 决策点 1） | 全程 |

> **注意 P1 与旧定位的区别**：在加固计划里 Linux 曾是"最清晰的可辩护空白"（独立战略）。
> 本路线图把它**降为发行战术**——因为"可靠层"定位不靠平台差异化立足，Linux 是获得早期用户的
> 低成本入口，而非护城河。护城河是 H1~H3 的工程能力。

## 7. 定位 → 补丁收缩：一条可验证的连锁

这是本路线图**唯一**能把战略直接兑换成工程收益的链条，因此单独列出：

```
定位从"桌面产品"收敛为"可靠层"
   → 不再需要自造桌面插件包（dshmarket / preset-transfer / …）
   → 3 个 functional 补丁失去存在理由（它们只是为挂载这些包而存在）
   → 补丁维护税下降，上游升级成本下降
```

**判据（可证伪）**：`patches/LAYERS.md` 中 3 个 `functional` 补丁的 `retireWhen` 全部指向
"官方提供声明式扩展点"。**只要项目还在自造插件包，这些补丁就不能退役。** 因此
"减少补丁"不是一个独立工程任务，而是**定位收缩的因变量**——把补丁当目标去删，方向就错了。

## 8. 需要裁决的冲突（本路线图的核心价值）

既有文档之间**存在真实冲突**，批次 F 的归档决定与更早的 redesign 设计不一致。不裁决，执行者会在
两份文档间反复横跳。以下是必须由项目所有者拍板的点。

### 决策点 1 — 定位主轴

- **A（推荐）— Reliability / Compatibility / Distribution Layer**：采纳 §3 定位。保住工程护城河，
  避开与官方桌面的正面竞争。**代价**：接受"不做炫酷桌面功能"，短期用户增长慢。
- **B — Linux-first 桌面产品**：继续做完整桌面客户端，靠官方不支持的平台立足。
  **代价**：与曲线 B 正面相撞，且护城河（可靠性）不构成用户可感知差异。
- **C — 维持自用**：只做 H0 加固，不资产化、不做兼容层。**代价**：放弃最有价值的长期产出。

> 外部评审与本仓库 redesign 文档独立得出同一结论（A）。除非有强理由，建议 A。

### 决策点 2 — Model Gateway：复活为 `dsh-provider-compat`？

**冲突**：redesign 文档 §Phase 5 要 Model Gateway 2.0；批次 F（2026-09-10）已将其**归档删除**；
外部评审建议**复活为独立于 Desktop 的 `dsh-provider-compat`**。

**裁决必须过归档文档自己的门槛**（`docs/archive/model_gateway_design.md`）：
- 退出条件 ②"连续两个 DSH 小版本仍无接线计划" → 正是当初归档的理由；
- **接线前置**：必须登记接线点、消费者、失败降级策略、以及"官方覆盖后如何摘除"的回归验证。

- **A（推荐）— 暂不复活，仅登记"待消费者"**：Tool Calling 兼容确是真痛点，但**没有真实消费者的
  兼容层会重蹈归档覆辙**。先在 H2 的回归语料中**度量**该痛点是否真实存在，再决定。
- **B — 复活为独立 runtime 侧组件**：仅当能写出接线前置四要素（见上）时，才开工。
- **C — 永久不做**：接受官方适配器的覆盖能力。

### 决策点 3 — 插件分级隔离：是否推进

**冲突**：redesign 文档 §7 有 Tier 0/1/2 进程隔离；批次 F 归档了 `plugin_worker.rs` /
`plugin-worker-host.mjs`，判据是"不在真实插件挂载路径上"；外部评审重提 4 级表，但**自己也说
必须与官方 loader 对齐**。

- **A（推荐）— 先做"插件可靠性契约"，隔离后置且条件化**：立刻可做的是
  **诊断 + 归因 + 恢复**（本仓已有 `formatFaultDetails` 与恢复页）；进程级隔离只在
  "能与官方 Cordis mount path 对齐"时才做。**不得再自造脱离官方 loader 的"假隔离"。**
- **B — 立即按官方 loader 对齐做隔离**：需先确认官方 mount path 是否暴露可挂载的隔离点。

### 决策点 4 — 上游推进目标版本（沿用加固计划）
A 稳妥（先 `0.1.2-rc.1`）/ B 激进（直追 `0.1.5-rc.*`）。

### 决策点 5 — 门禁强度与 CI 成本（沿用加固计划）
GUI 冒烟与 POSIX fault-inject 是否转硬门禁（可折中：mac/win 硬、Linux 软）。

### 决策点 6 — 签名密钥策略（沿用加固计划）
单密钥 + runbook，还是双公钥过渡？

## 9. 推荐投入比例

> 这是**方向性配比**，不是精确预算。前提是决策点 1 选 A。

| 领域 | 建议占比 |
|------|---------|
| Supervisor / Runtime reliability（H1） | 35% |
| Compatibility / Tool Calling（H2、决策点 2） | 20% |
| Plugin diagnostics / recovery（决策点 3 的 A 案） | 15% |
| Packaging / update / release engineering（H3） | 15% |
| Desktop UX（仅保住体验不倒退） | 10% |
| Experimental | 5% |

**解读**：桌面 UX 只保留 10% —— 不是"不修 bug"，而是**不再把新增桌面功能当作研发主线**。

## 10. 明确不做

- **不重做官方聊天 UI**（同步成本持续净负）。
- **不做自定义 Agent Runtime / Agent Loop**（一旦出现 `Tauri Agent Loop`，项目即脱离 DSH）。
- **不写第二套 Provider 适配逻辑**，除非过决策点 2 的门槛。
- **不把移动端功能作为核心竞争力**（可作为可选模块，不做主线）。
- **不为 Harness 远程 origin 开反向 IPC**（INV-2，不因任何产品需求破例）。
- **不做皮肤 / 桌面宠物 / SSH 面板**（非差异化，且与"可靠"定位相悖）。
- **不在 `push` 上恢复全量 CI**（H0-c 的 nightly / preflight 是替代路径）。

## 11. 风险与假设

| 风险 / 假设 | 说明 | 应对 |
|-------------|------|------|
| **外部事实会过期** | 官方桌面"未发布、无 GA"是 2026-09-12 的核实状态；随时可能变 | 每个阶段开工前复核 §附录；决策点 1 的答案可能因官方发布而改变 |
| **官方桌面一旦发布** | 若它覆盖了 reliability 场景（含诊断/恢复），H1 的护城河会被压缩 | H1 的目标就是"不依赖官方存亡"的可复用组件；同时评估"补充形态"（P2） |
| **上游破坏性变更** | 曲线 A 随时可能打断打包链路 | H0-a 漂移哨兵 + H2 兼容矩阵 + §5.3 补丁退役 |
| **单人 bus factor** | 关键知识集中在一个人 | H0-e 的三份 runbook 即为降低此风险 |
| **兼容性语料被误读** | 跑通语料 ≠ 模型调用正确 | §5.2 已写明诚实约束，对外不得夸大 |
| **定位收缩导致用户流失** | 从"功能丰富的桌面客户端"退为"可靠层"可能不讨喜 | 这是决策点 1 的**已知代价**，需接受 |

## 12. 一句话总结

**当前项目是"工程能力高于产品定位成熟度"的典型。长期规划的全部内容，就是把工程能力兑换成
一个清晰的定位：做官方 DSH 之上的可靠运行时、兼容性与发行增强层——而不是再做一个会被官方
收走的桌面壳。**

**执行入口**：先做 H0（加固计划批次 H~M）+ H0-f（边界契约），同时裁决 §8 的决策点 1~3；
用决策点 1 的答案解锁 H1。
