## 5. 验证纪律

1. **红→绿成对**：先说清「改之前哪条会红」，再给「改之后绿」的证据。只给绿不构成取证。
2. **注入必须打在被测机制本身**：CD02 的 E8 夹具要植入**命令体内的裸 `return Err`**，而非删掉整个命令让它因「找不到定义」而红。
3. **空集不得冒充通过**：CD13/CD14/CD18/CD19 都涉及扫描或解析，解析失败或扫出 0 条必须判红。
4. **判据不得与被检对象同源**：不拿被测脚本自己的输出证明它对。
5. **穷尽式列举必须用词界精确匹配，并排除 `.delta/`**。
6. **不在本机跑 cargo build/test/clippy 就不得宣称通过**（见 §10）。
7. **【V2 新增】独立提交**：CD08、CD10、CD15、CD17 四项**必须独立提交、独立验证**——它们分别触及安全边界、异步执行、协议处理与安全敏感模块，混在大改动里无法回滚也无法定位回归。
8. **【V2 新增】阶段 0 存证**：每条 CD 在动代码**之前**先记录其红/绿现状，否则事后无法证明「改前是红的」。

## 7. 项目级验收维度（V2 新增）

> 以下三项不属于任何单个 CD，但缺了它们，「修完 23 项」不等于「项目可信」。这是评估指出的、V1 缺失的部分。

### 7.1 运行时兼容性矩阵

项目同时涉及 DSH 上游版本、Node 版本、三平台、双通道、补丁集合、vendor 依赖。需要一份正式矩阵作为**每次上游升级的必经门禁**：

| 维度 | 验收要求 |
|---|---|
| DSH 版本 | 精确锁定（`harness-locks/dsh-releases.json` 台账） |
| Node 版本 | 明确支持范围（`engines.node`） |
| Runtime Target | 与上游版本对应（`runtime-locks/primary-runtime.json`） |
| Patch | 全部通过适用性检查（`check-patch-applicability` ±20 窗口） |
| Windows | 启动、退出、更新、恢复 |
| macOS | 启动、退出、更新、恢复 |
| Linux | 启动、退出、更新、恢复 |
| Release Channel | rc / alpha **各自独立验证**，不互相代表 |

**建议**：不新建文档，纳入 `docs/release-runbook.md`（在役 runbook），避免又开一处状态源。

### 7.2 发布前验证闭环

**不恢复 push 全量 CI**（ADR-030）。改为把发布流程做可靠：

```
准备发布 → 检查当前 HEAD → 运行 CI workflow → 运行 Smoke workflow
  → 检查 Runtime Lock → 检查 Patch Applicability
  → 检查版本与 Release Manifest → Release Preflight → 打 Tag / 发布
```

**发布证据记录**（每份 Release 必须能回答）：
- 测试对应哪个 commit；
- Smoke 对应哪个 commit；
- Runtime 对应哪个版本；
- 最终产物对应哪个 commit。

**核心目的**：消除「测了 A 提交、发布 B 提交」这一形态。此项应落到 `release.yml` 的 preflight，作为硬前置而非流程约定。

### 7.3 性能基线与回归监测

V5 已裁「先测量后优化」，本档**不承诺任何性能改善**。但需先形成**可重复执行的测量方式**：

| 指标 | 监测目标 |
|---|---|
| Harness 冷启动时间 | 基线与回归 |
| Supervisor 响应时间 | 避免阻塞 |
| IPC 响应时间 | 避免事件循环阻塞 |
| 更新事件频率 | 避免事件洪泛（CD23 的判据） |
| 日志读取时间 | 避免大文件拖慢 UI（CD10 的判据） |
| 内存占用 | 发现异常增长 |

**边界**：不建设复杂 Benchmark 系统；内存/CPU 按 external-assessment §2 裁定 7 走**文档化手工法**。此项与 **V5** 是同一件事，**不另立项**。

## 8. 定位与技术债红线（V2 新增）

### 8.1 与官方桌面端的差异定位

不能再以「用 Rust + Tauri 替代 Electron」作为主要竞争优势——官方已有 Tauri 2 桌面端。本项目的差异化应落在官方覆盖不足处：

| 维度 | 本仓 | 官方桌面端 |
|---|---|---|
| 核心定位 | 独立桌面宿主 | 官方桌面产品 |
| Runtime | 自带 Node + DSH 依赖树 | 官方裁剪后端 |
| 上游适配 | 自定义补丁、vendor | 官方维护 |
| 版本策略 | 双通道 + 独立版本账本 | 跟随官方发行 |
| 进程管理 | 独立 Supervisor | 官方生命周期 |
| 诊断体系 | 自建日志、崩溃归因、恢复 | 官方实现 |

**应长期保留的四项核心竞争力**：Runtime Reliability（进程生命周期 / Supervisor / 孤儿清理 / 崩溃恢复）、Runtime Compatibility（上游适配 / 补丁 / 双通道 / 依赖锁定）、Diagnostics（故障归因 / 日志 / 诊断包 / 更新失败分类 / Safe Mode）、Desktop Integration（托盘 / 移动桥 / 原生通知）。

### 8.2 长期技术债红线

- 不重写官方 Agent / Tool / MCP。
- 不重复建设 Model Gateway。
- 不为没有消费者的抽象层造消费者。
- 优先使用官方公开接口。
- Patch 必须有适用性检测、失效报告、退役条件。
- 上游升级必须有兼容性验证（§7.1）。
- **CD15 是协议治理的范例，不是第二套网络协议框架的起点**。

### 8.3 阶段定位：Reliability First

当前阶段**不扩张功能**，集中完成安全、核心契约、更新链路、生命周期可靠性治理，再做结构优化。这比增加功能或追求全 Rust 化更符合项目阶段。
